  <behavior>
    - Test: Admin role allows tools/call for ANY tool name
    - Test: Admin role allows tools/list, resources/read, prompts/get, initialize
    - Test: Read-only role allows tools/list (can see tools)
    - Test: Read-only role DENIES tools/call (cannot execute tools)
    - Test: Read-only role allows resources/read and prompts/get
    - Test: Restricted role allows tools/call ONLY for tools in its allowed_tools list
    - Test: Restricted role DENIES tools/call for tools NOT in its allowed_tools list
    - Test: Restricted role's tools/list response is filtered to show only allowed tools
    - Test: Unknown role defaults to deny-all
    - Test: initialize method is allowed for ALL roles (required for MCP handshake)
    - Test: Engine loaded from config.RoleConfig correctly maps role names to permissions
  </behavior>
  <action>
Create `internal/rbac/roles.go`:

Define the 3 built-in roles as constants and default configurations:
```go
const (
    RoleAdmin      = "admin"
    RoleReadOnly   = "readonly"
    RoleRestricted = "restricted"
)
```

- `func DefaultRoles() []config.RoleConfig` — returns the 3 built-in role configs. Admin: no tool restrictions. ReadOnly: deny_tools includes all tools/call (handled by engine logic, not per-tool). Restricted: allowed_tools must be explicitly configured.

Create `internal/rbac/engine.go`:

- `type Engine struct` — holds role->permissions map built from config, implements Middleware interface.
- `type Permission struct` — AllowedMethods (set of MCP methods), AllowedTools (set of tool names, empty = all for admin), DenyTools (set of tool names).
- `func NewEngine(roles []config.RoleConfig) *Engine` — builds permission map from config.
- `func (e *Engine) Process(ctx context.Context, req *proxy.MCPRequest, identity *proxy.ClientIdentity) (*proxy.MCPRequest, error)` — implements Middleware interface:
  1. Look up permissions for identity.Role
  2. If role unknown, return Forbidden error
  3. Always allow "initialize" (all roles need MCP handshake)
  4. Check if method is in AllowedMethods for the role
  5. For tools/call: extract tool name, check against AllowedTools/DenyTools
  6. Return nil error to allow, non-nil error to deny
- `func (e *Engine) FilterToolsList(identity *proxy.ClientIdentity, toolsList json.RawMessage) (json.RawMessage, error)` — for tools/list responses, filters the returned tools array to only include tools the client's role can access. Admin sees all, readonly sees all (can list but not call), restricted sees only allowed_tools.

Role logic:
- Admin: AllowedMethods = all, AllowedTools = all (empty set means unrestricted)
- ReadOnly: AllowedMethods = {initialize, tools/list, resources/read, prompts/get}, DenyTools = all (tools/call denied entirely)
- Restricted: AllowedMethods = {initialize, tools/list, tools/call, resources/read, prompts/get}, AllowedTools = configured set only

Write tests FIRST (RED), then implement (GREEN).

Create `internal/audit/logger.go`:

- `type Logger struct` — implements AuditLogger interface. Holds output writers (stdout, file, or both), mutex for thread safety, enabled flag.
- `func NewLogger(cfg *config.AuditConfig) (*Logger, error)` — creates logger from config. Opens file if file output configured (append mode, create if not exists). Returns error if file can't be opened.
- `func (l *Logger) Log(entry middleware.AuditEntry)` — marshals entry to JSON, writes as single line. If "both" output, writes to both stdout and file. Thread-safe via mutex.
- `func (l *Logger) Close() error` — flushes and closes file handle if open.

JSON output format (one object per line, JSONL):
```json
{"timestamp":"2026-03-19T14:30:00.000Z","client_id":"user123","session_id":"abc-def","method":"tools/call","tool_name":"read_file","allowed":true,"denied_reason":"","latency_ms":45,"request_id":"req-xyz"}
```

Use `encoding/json.Marshal` for each entry. Timestamps as RFC 3339 (ISO 8601) in UTC. latency_ms as integer milliseconds.

For stdout: write to os.Stdout with newline. For file: write to *os.File with newline. Mutex wraps the write to prevent interleaved lines from concurrent requests.

Write tests FIRST using bytes.Buffer as the writer (injectable for testing), then implement.

  <behavior>
    - Test: Client under rate limit is allowed (returns true)
    - Test: Client exceeding rate limit is denied (returns false)
    - Test: Rate limits are per-client (client A at limit does not affect client B)
    - Test: Burst allows short spikes above sustained rate
    - Test: Rate refills over time (denied client can retry after waiting)
    - Test: New/unknown client gets a fresh limiter (not pre-denied)
    - Test: Configurable rates per client from config
  </behavior>
  <action>
Create `internal/ratelimit/limiter.go`:

- `type Limiter struct` — implements RateLimiter interface. Holds per-client rate.Limiter instances in sync.Map. Uses `golang.org/x/time/rate` for token bucket algorithm.
- `func NewLimiter(cfg *config.RateLimitConfig) *Limiter` — creates limiter from config. Converts requests_per_minute to rate.Limit (per second). Sets burst from config.
- `func (l *Limiter) Allow(clientID string) bool` — gets or creates rate.Limiter for clientID, calls limiter.Allow(). Thread-safe via sync.Map.
- `func (l *Limiter) getOrCreate(clientID string) *rate.Limiter` — lazy initialization of per-client limiter. Uses sync.Map.LoadOrStore for atomic get-or-create.
- `func (l *Limiter) Cleanup()` — periodic cleanup of stale client limiters (not accessed in 10 minutes). Called by background goroutine if needed, or on-demand.
- `func (l *Limiter) Stop()` — stops cleanup goroutine.

Conversion: requests_per_minute / 60.0 = rate.Limit (requests per second).
Default: 100 req/min = ~1.67 req/sec, burst of 10.

Use `golang.org/x/time/rate` (already in go.mod from Plan 01). This is the standard Go token bucket implementation. No need for custom algorithm.

Write tests FIRST (RED), then implement (GREEN). Use time-based testing with short intervals (not sleep-based -- use rate.NewLimiter directly with known rates for deterministic tests).
